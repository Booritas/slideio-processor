The tests cover the identical-results half on synthetic scenes (`TileExecutor.ResultsIdenticalAcrossWorkerCounts`, `Seg3.IdenticalAcrossWorkerCounts`), that tiles run concurrently within the memory budget (`TileExecutor.BudgetBoundsConcurrentTiles`), and that seam merging stays within it by spilling rather than waiting (`SeamSpill.FullyHeldBudgetSpillsInsteadOfWaiting`, `SeamRun.TightBudgetDoesNotWaitForMemory`). Each tile's reservation also counts its operations' declared working sets (`tests/pipeline/test_working_set.cpp`), and the algorithm tests check every built-in's declaration against its measured allocations.
- **UR-EXT-4 (the framework supplies tiling, budgeting, threading and persistence).** Partly covered. `tests/pipeline/test_working_set.cpp` declares it for the budgeting half that extends to operations: an operation states its own working memory and the framework reserves it with each tile and refuses a run that does not fit. Otherwise it is declared only by the test-support operations (`tests/pipeline/test_support/global_ops.cpp`), which contain no threading, memory-management or storage code.

## algorithm

IDs are those the tests under `tests/algorithm/` declare. The module so far holds its registry, the point operations — the fixed, Otsu and adaptive thresholds, explicit type conversion, colour space conversion and stain deconvolution — and the filters and morphology: the Gaussian, median, Sobel, Scharr, Laplacian, Canny and bilateral filters, and erode, dilate, open and close with structuring elements (SDS 06 §6.1–6.6). `tests/algorithm/test_registry.cpp` checks that every built-in is registered at load, that registration is idempotent and thread-safe, that every built-in passes the operation conformance check (its declarations equal the catalog's, and re-creating it from its own parameters gives equal declarations and parameters) and carries a correctness reference and a complexity note, and that the support-matrix rows match each operation's runtime contract. Each operation's test file checks its correctness reference to the tolerance SDS 06 §6.9 states, the typed factory against the name path, and, where the operation runs through a pipeline, tiled output against one tile. A separate executable, `slideio_processor_working_set_tests`, counts the module's own allocations with a replaced global `operator new` (`tests/algorithm/support/allocation_meter.hpp`, checked by `tests/algorithm/test_allocation_meter.cpp`); `tests/algorithm/test_working_set_pixel.cpp` and `tests/algorithm/test_working_set_filter.cpp` check that every built-in's measured peak for one call stays within its declared working set, with OpenCV's analytically bounded share subtracted, and that a run whose working set does not fit the ceiling is refused.

### Not covered by `algorithm` tests

- **UR-SEG-1 to UR-SEG-8 (segmentation and measurements).** These operations do not exist yet; `registerSegmentationOperations()` and `registerMeasurementOperations()` register nothing.
- **UR-QA-2 for `pixel.canny`, unconditionally.** `tests/algorithm/test_canny.cpp` declares UR-QA-2 and checks tiled output against one tile where every edge is strong, and that on a weak chain longer than the declared reach tiling only drops pixels beyond 32 pixels of every strong one. Exact agreement on every input is not claimed: hysteresis has unbounded reach, which is open question 15 in `requirements.md` (SDS 06 §6.4).
