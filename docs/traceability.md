### Not covered by `pipeline` tests

- **UR-EXE-2 (throughput from 1 to 4 workers).** The acceptance check, that throughput on the reference slide improves materially from 1 to 4 workers while results stay identical, is a manual performance check. It was not run. The tests cover the identical-results half on synthetic scenes (`TileExecutor.ResultsIdenticalAcrossWorkerCounts`, `Seg3.IdenticalAcrossWorkerCounts`), that tiles run concurrently within the memory budget (`TileExecutor.BudgetBoundsConcurrentTiles`), and that seam merging stays within it by spilling rather than waiting (`SeamSpill.FullyHeldBudgetSpillsInsteadOfWaiting`, `SeamRun.TightBudgetDoesNotWaitForMemory`). Each tile's reservation also counts its operations' declared working sets (`tests/pipeline/test_working_set.cpp`), and the algorithm tests check every built-in's declaration against its measured allocations.
- **UR-EXT-4 (the framework supplies tiling, budgeting, threading and persistence).** Partly covered. `tests/pipeline/test_working_set.cpp` declares it for the budgeting half that extends to operations: an operation states its own working memory and the framework reserves it with each tile and refuses a run that does not fit. `tests/pipeline/test_object_finishing.cpp` declares it for object persistence: the framework normalises, filters and finishes every object an operation emits, whole or merged, so the operation writes no merging or finishing plumbing. Otherwise it is declared only by the test-support operations (`tests/pipeline/test_support/global_ops.cpp`), which contain no threading, memory-management or storage code.

## algorithm

IDs are those the tests under `tests/algorithm/` declare. The module so far holds its registry, the point operations — the fixed, Otsu and adaptive thresholds, explicit type conversion, colour space conversion and stain deconvolution — and the filters and morphology: the Gaussian, median, Sobel, Scharr, Laplacian, Canny and bilateral filters, and erode, dilate, open and close with structuring elements (SDS 06 §6.1–6.6). `tests/algorithm/test_registry.cpp` checks that every built-in is registered at load, that registration is idempotent and thread-safe, that every built-in passes the operation conformance check (its declarations equal the catalog's, and re-creating it from its own parameters gives equal declarations and parameters) and carries a correctness reference and a complexity note, and that the support-matrix rows match each operation's runtime contract. Each operation's test file checks its correctness reference to the tolerance SDS 06 §6.9 states, the typed factory against the name path, and, where the operation runs through a pipeline, tiled output against one tile. A separate executable, `slideio_processor_working_set_tests`, counts the module's own allocations with a replaced global `operator new` (`tests/algorithm/support/allocation_meter.hpp`, checked by `tests/algorithm/test_allocation_meter.cpp`); `tests/algorithm/test_working_set_pixel.cpp` and `tests/algorithm/test_working_set_filter.cpp` check that every built-in's measured peak for one call stays within its declared working set, with OpenCV's analytically bounded share subtracted, and that a run whose working set does not fit the ceiling is refused. The segmentation operations — connected components, contours, marker-controlled watershed and tissue detection (SDS 06 §6.7) — and their per-object measurements (§6.8) complete the catalog at twenty-one operations: the shared region tracer and emission (`tests/algorithm/test_region_trace.cpp`) and measurement finishing with calibration (`tests/algorithm/test_measurement_finish.cpp`) are tested on their own, each operation's test file checks its analytic reference and its objects identical to one tile at three tile sizes, and `tests/algorithm/test_working_set_segment.cpp` bounds each one's measured peak, objects emitted included, by its declaration.

## workspace

IDs are those the tests under `tests/workspace/` declare. The module so far holds `Workspace` (SDS 04 §4.1): the directory binding one slide scene to a store, with its layout (`workspace.store`, its sidecars and raster directory, and `scratch/`), the slide binding kept in the store's provenance, the writer lock and the read-only open, the scratch clear and raster-file sweep at `open`, the undo of a failed `create`, and the one memory budget. It also holds `LayerLifecycle` (SDS 04 §4.6), which delegates layer declaration and drop to the store's `LayerRegistry`. It also holds `StageRegistry` (SDS 04 §4.3), which declares stages, derives their dependencies from reads, written layers and rasters and explicit `dependsOn`, rejects cycles and undeclared reads before writing anything, persists the record, written layers and dependency rows in one transaction (a failed declare changes nothing), treats a repeated name as a redeclaration (the same declaration changes nothing, a changed one re-derives and marks the stage and its dependents stale), marks staleness along the staleness graph (SDS 04 §4.5: layer reads, raster reads, layer ordering, derived-from and explicit dependencies, which may contain cycles) and answers what a re-run invalidates and why, and why a stage is stale now (from durable data, so the same after a reopen), through `StalenessGraph`, and restores every stage at `open` (a record that does not parse, or whose explicit dependency names the stage itself, is kept by name only and never runs; a `dependsOn` naming a stage not yet declared stays unresolved and the stage is not runnable); a read-only registry re-reads the stored stages when a live writer changed them, so an observer sees the writer's graph (UR-OBS-1). It also holds `StageDefinition` (SDS 04 §4.2), the durable identity of a stage, and its record (`stageRecordVersion` 1), which names every layer and raster and gives each raster binding name one input, is rebuilt into a definition on load, and compares declarations without regard to list order. The tests write their slide with libtiff (`tests/workspace/support/test_slide.cpp`) and open it through SlideIO's driver lookup. It also holds `StageRunner` (SDS 04 §4.4), which runs one declared stage: it refuses a read-only workspace, an unreadable stage, a stage with an incomplete or stale dependency and a second runner in the same workspace, then binds the stored definition to a `Pipeline`, binds the layer-backed and stored rasters it reads and the raster it writes, flushes the writers (objects, edges, annotations, then the raster last) and records the analysis level, `Complete` and the cleared stale flag; on a failure or cancellation it discards the stage's output, records `Failed` and re-throws a `StageError` (or `CancelledError`) naming the stage, the operation and the tile, and on a re-run, a stage left `Running` by a dead process included, it marks every stage the staleness graph reaches from it stale (`markAffectedStale`) and then discards the prior output; the tests run it on a slide of nine dark discs (`writeBlobSlide`). It also holds `declareCoarseToFine` and `CoarseToFineSpec` (SDS 04 §4.2), which validate a coarse-to-fine pair (distinct names and layers, strictly ordered explicit levels, both halves set) before declaring anything, then declare the two ordinary stages wired by `readsLayerAsRaster` and the restriction; a failing fine declare leaves the coarse stage declared.
